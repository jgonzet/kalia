# Synthetic dataset

Format of the files under `data/<company>/`. The reasons for each choice are in `docs/DECISIONS.md`; this file only says what the files contain. If a format changes, change it here first.

## Files

| File | Content |
|---|---|
| `company.json` | `id`, `name`, `description`, `user_id` (person id of the protagonist), `reference_date` (the "today" of the dataset), `held_out` (ids of documents left out of the initial load) |
| `people.jsonl`, `projects.jsonl` | the catalog, one record per line, each with a stable `id` and a `company` field |
| `ORGCHART.md` | generated by `scripts/orgchart.py`; never edited by hand |
| `story.md` | background facts of the company and its projects (see below) |
| `expected/<document id>.json` | the answer key of one document (see below) |
| `questions.jsonl` | the acceptance questions with their expected answers (see below) |
| `documents/<document id>.md` | the generated texts: a metadata header plus free text. Not created yet |

Prompts for the external generator live in `data/generation/`, shared by all companies. Not created yet.

Document ids are `<company>-NNNN`, unique across companies.

## `story.md`

Markdown, pasted whole into every generation batch. A blockquote header states the rules; then a `## Empresa` section for facts that cross projects and one `## <project name> (<project id>)` section per project, each with a `Situación:` paragraph and a `Hechos:` list of dated facts (`- YYYY-MM-DD — text`). Facts are true in every document.

## `expected/<document id>.json`

| Field | Content |
|---|---|
| `document_id`, `company`, `type` (`email`, `meeting` or `chat`), `date` | repeated from the document header; they must match it |
| `participants` | person names as written in `people.jsonl`; includes the user |
| `projects` | project names as written in `projects.jsonl`; empty when none |
| `author` | emails only: the sender |
| `brief` | one line saying what the document is about; what the generator reads |
| `extractions.commitments` | list of commitments (below). The key `extractions` missing means "designed, not annotated yet"; an empty list means "annotated, nothing to extract" |
| `mentions` | ids of commitments of other documents that this text names without promising them again |
| `not_commitments` | phrases the text must contain that are not commitments (conditionals, hypotheses); an extractor that returns them makes a false positive |
| `text_sha256` | hash of the accepted text; `null` until the document is accepted |

A commitment: `id` (`<document id>-cN`), `who`, `to_whom`, `what`, `due` (`YYYY-MM-DD` or `null`), `due_text` (the deadline phrase as the text says it, or `null`; for diagnosis only, the app does not use it) and `project` (name or `null`).

A commitment exists only if the text shows the person accepting it; in an email the reply is inside the same document. Each commitment is promised in one document only.

## `questions.jsonl`

One question per line: `id`, `version`, `acceptance` (`Q1` to `Q5`, the questions of `docs/SPEC.md`), `question`, `expected` and `after_held_out`.

- `expected`: ids of the commitments the answer must contain after the initial load, that is, every document except those in `held_out`.
- `after_held_out`: `null`, or `{"document": <id>, "expected": [...]}` with the answer once that document is ingested (question 5 only).
- A published question is never edited; new or changed questions get a new `version`.

Rules the answers are computed with:
- "This week" is the commitments whose `due` falls between `reference_date` and six days later; overdue and undated commitments are left out.
- Every commitment counts as open (V0 has no status).
- "Involves X" includes the commitments that do not involve the user.
- "My boss" is the user's boss in the catalog, not other levels above.
