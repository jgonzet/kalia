# KALIA — V0 Spec

> This document covers V0 only. Product direction and future expansions live in `docs/VISION.md`.

## Problem

Managers, PMs and tech leads with many projects, many meetings and complex stakeholders spend effort mentally reconstructing what is going on: who committed to what, and by when. That context lives scattered across emails, meeting transcripts and chats.

## User

A manager, PM or tech lead juggling multiple projects and stakeholders. V0 models a single user: the protagonist of the synthetic dataset.

## What V0 is

The first slice of the product described in the vision: it reads unstructured work documents, extracts commitments from them, stores them, and answers the user's questions in a chat using that stored context.

It validates the base pipeline (documents -> structured context -> answers) for a single user, with no proactive behavior. It is not a task manager, a dashboard or a generic chatbot. The goal of V0 is to validate the end-to-end flow and start collecting feedback, not to define the final architecture or maximize answer quality.

A "document" is any single piece of input: an email, a meeting transcript or a chat conversation.

## Core flow

```text
Catalog (people, projects) + documents (emails, transcripts, chats)
        -> Extraction (LLM): commitments, linked to catalog people and projects
        -> Structured storage

User question -> Retrieval over stored commitments -> LLM -> Grounded response
```

V0 is complete when this flow works end-to-end on a local machine.

## In scope

- Local application running on a single PC.
- Ingesting the synthetic dataset: a catalog of people and projects, plus documents, ingested one at a time (including after the initial load).
- LLM-based extraction of **commitments** from the documents: who committed, to whom, to do what, and by when.
- Linking each commitment to the people and projects in the catalog, by name.
- Participants of each document come from the document's metadata. Each person's role, hierarchy level and who they report to come from the catalog. The relationship of each person to the user (boss, peer, report) is derived from the catalog hierarchy. None of this is extracted by the LLM.
- Persistent storage of the extracted commitments.
- Retrieval of the commitments relevant to a question.
- Simple chat interface.
- Responses generated by an LLM using the retrieved commitments.
- Replaceable LLM: local models and API-based models can be swapped without changing the rest of the application.
- Docker-based setup, so the application can run on another PC.
- A smoke test of the core flow.

## Design constraints

Derived from the vision, so V0 does not have to be rewritten as the product grows:

- Ingestion is source-agnostic: every input becomes a normalized document (type, date, participants, text). Adding a source later means adding an adapter, not changing the rest.
- Ingestion is incremental and idempotent: loading the same document twice does not duplicate its commitments. A document is identified by its id.
- The reference date ("today", used by questions such as "due this week") comes from configuration, defaulting to a date defined by the dataset.
- Relative deadlines in a document ("by Friday") are resolved against that document's date; a commitment without a deadline has a null one.
- Every extracted commitment is open: V0 has no commitment status or closing.
- Every stored commitment has a stable id, links to catalog entities, and a reference to its source document and that document's date.
- Every stored record belongs to an owner (the user). V0 has a single owner.
- Ingestion, extraction, storage, answering and the LLM provider are separate modules with explicit interfaces, so each can evolve independently. Module boundaries are decided in the plan.

## Out of scope

- Extraction of anything other than commitments (blockers, decisions, topics, etc.).
- Inference, from the documents, of people's roles and of relationship attributes (hierarchy, tone such as warm, cold or authoritarian, sentiment, formality, urgency, tension). V0 takes roles and hierarchy from the catalog.
- Proactive behavior of any kind: prioritization, risk detection, suggested focus, notifications.
- Generated outputs: email drafts, follow-ups, reminders, summaries, meeting preparation and minutes.
- Live meeting listening.
- Asking the user for clarification; per-user learning.
- Network of avatars and access privileges between users.
- Resident background process; V0 runs on demand.
- Entity resolution beyond matching against the known catalog; entity merging.
- Evolution of context over time; graph engines or knowledge graphs.
- External integrations (mail, calendar, chat tools); calendar ingestion.
- Agents and autonomous actions.
- Authentication and multi-user support.
- Production infrastructure and advanced observability.
- Advanced UI and dashboards.
- Billing.
- Premature optimization.

If something is not necessary for the core flow or for the design constraints above, it does not go in V0.

## V0 dataset and acceptance questions

- **Catalog:** one fictional company, its active projects (name, description, status, deadline), its people (name, role, area, hierarchy level, reports to), and the protagonist user.
- **Documents:** 25 documents written for the fictional company, mixing the three types (email, meeting transcript, chat), each with date and participants. Most are short; two meeting transcripts are longer (up to about 1200 words) to exercise long inputs.
- **Content language:** Spanish.
- **Acceptance questions:**
  1. What did I commit to a given person, and what did that person commit to me, and by when?
  2. Which commitments are due this week?
  3. Which open commitments involve a given person?
  4. Which commitments do I have with my boss?
  5. After one new document is ingested, does a question related to it return an answer that reflects it?

## Definition of done

1. The application starts locally with a single documented command.
2. The synthetic dataset can be ingested document by document and processed into stored commitments.
3. A user can ask a question through the chat interface.
4. The system retrieves the stored commitments relevant to the question.
5. The LLM generates a response using those commitments.
6. Each acceptance question above gets a response grounded in the loaded context.
7. The application runs on another PC following the documented setup.

## Development rule

Do not design the final product during V0. When a limitation or a new requirement appears, evaluate it against the current product need. Build the smallest thing that works, then evolve it based on what is learned.
